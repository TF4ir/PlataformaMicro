# P0.1 — Auditoría y endurecimiento de Autenticación / Autorización

- Fecha: 2026-11-09
- Alcance: `apps/web/` (Next.js App Router) + una migración SQL justificada en `supabase/migrations/`
- Estado: implementado, pendiente de revisión. Sin commits ni despliegues.

## 1. Resumen ejecutivo

Antes de este cambio la autorización del frontend se basaba en dos cookies
escritas por el navegador:

- `nexo_session = "session_active_" + Date.now()`
- `nexo_role = "student" | "teacher"`

El middleware sólo comprobaba su presencia/valor. Cualquier visitante podía
crearlas desde la consola y abrir rutas docentes. Además, `RoleProvider` confiaba
en `user.user_metadata.role` (editable por el usuario) y la política RLS
`profiles_update_own` permitía actualizar el propio `role`, `tenant_id` y
`student_code`, habilitando escalada de privilegios persistente.

El flujo actual deriva la identidad exclusivamente de una sesión Supabase
verificada en servidor (`auth.getUser()`) y el rol de `public.profiles.role`.
Las cookies `nexo_*` ya no se leen ni se escriben; sólo se limpian.

## 2. Flujo anterior (vulnerable)

```text
Navegador
  │  document.cookie: nexo_session / nexo_role / nexo_user_name
  ▼
middleware.ts
  │  isAuthenticated = Boolean(nexo_session && role ∈ {student, teacher})
  │  redirects por valor de nexo_role
  ▼
RoleProvider (cliente)
  │  user_metadata.role  →  nexo_role (fallback)
  │  login() escribe cookies de sesión y rol
  ▼
Login demo (NODE_ENV !== production)
  │  credenciales hardcodeadas → login("student" | "teacher")
  ▼
API FastAPI
  │  X-User-Id / X-Tenant-Id / X-User-Role en modo demo
  ▼
Supabase
     profiles_update_own: UPDATE libre de la propia fila (incluye role)
```

## 4. Flujo actual (endurecido)

```text
Navegador
  │  Cookies de Supabase Auth (gestionadas por @supabase/ssr)
  ▼
middleware.ts (Edge, async)
  │  1. ¿Hay cookie de auth?  ── no ──► role = null
  │  2. createServerClient(cookies req/res)
  │  3. supabase.auth.getUser()  ── inválida/expirada ──► role = null
  │  4. SELECT role FROM profiles WHERE id = user.id (RLS propia)
  │  5. normalizeRole(profile.role)  ── desconocido ──► role = null
  │  6. decideRoute(role, pathname)  [módulo puro]
  │  7. propaga cookies refrescadas en allow/redirect/deny
  ▼
RoleProvider (cliente)
  │  getUser() + profiles.role  → estado visual únicamente
  │  login(user) sólo navega; no crea cookies
  │  logout → supabase.auth.signOut() + limpieza de cookies legacy
  ▼
API FastAPI (sin cambios de contrato)
  │  Authorization: Bearer <Supabase JWT>
  │  Firma/issuer/audience/expiración/identidad/permisos validados en backend
  ▼
Supabase
     RLS + privilegios de columna + trigger anti-escalada en profiles
```

La autorización real ocurre en tres capas independientes:

1. **Middleware**: navegación y separación de portales.
2. **Backend FastAPI**: valida el JWT y resuelve permisos desde `profiles`.
3. **RLS/privilegios Postgres**: aislamiento por fila y por columna.

Ninguna capa confía en la anterior para datos que pueda fabricar el cliente.

## 5. Matriz de autorización

Roles de base de datos: `student`, `teacher`, `admin`, `super_admin`, `researcher`.
La UI web sólo renderiza portales `student` y `teacher`.

| Ruta | Anónimo | student | teacher | admin / super_admin | researcher |
| --- | --- | --- | --- | --- | --- |
| `/login`, `/recovery` | Permitido | Redirige a `/dashboard` | Redirige a `/teacher/dashboard` | Redirige a `/teacher/dashboard` | Sin portal web (login denegado) |
| `/` | Redirige a `/login` | Redirige a `/dashboard` | Redirige a `/teacher/dashboard` | Redirige a `/teacher/dashboard` | Redirige a `/system-status` |
| `/dashboard`, `/courses`, `/progress`, `/learn/*`, `/quiz/*`, `/recommendations/*` | Redirige a `/login?redirect=…` | Permitido | Redirige a `/teacher/dashboard` | Permitido | 403 |
| `/teacher/*` (incluye `/teacher/questions`) | Redirige a `/login?redirect=…` | Redirige a `/dashboard` | Permitido | Permitido | 403 |
| `/admin/*` | Redirige a `/login?redirect=…` | 403 | 403 | Permitido | 403 |
| `/system-status` | Redirige a `/login?redirect=…` | Permitido | Permitido | Permitido | Permitido |
| Rutas no clasificadas | Redirige a `/login?redirect=…` | Permitido | Permitido | Permitido | Permitido |
| `/api/*` | No interceptado por middleware; FastAPI/Route Handler valida JWT | — | — | — | — |

Decisiones de redirección/denegación:

- `unauthenticated` → `302 /login?redirect=<ruta>`.
- `wrong-role` entre portales → `302` al home del rol verificado.
- `forbidden-role` (`/admin` y roles sin portal) → `403 Forbidden`.
- `safeRedirectForRole` sólo acepta rutas locales permitidas; bloquea
  `https://…`, `//…` y rutas de otro rol.

## 6. Cambios implementados

### 6.1 Nuevo módulo puro

`apps/web/src/lib/auth/authorization.ts`

- `normalizeRole`, `portalRoleFor`, `homePathForRole`.
- `classifyRoute`, `decideRoute`, `safeRedirectForRole`.
- Sin I/O, sin cookies, sin headers: testeable y reutilizable por middleware,
  Route Handlers y pruebas.

### 6.2 Middleware

`apps/web/src/middleware.ts`

- `createServerClient` con cookies de request/response.
- `auth.getUser()` (validación contra Supabase Auth) en lugar de confiar en
  cookies.
- Rol leído de `public.profiles`.
- `decideRoute` centraliza redirecciones, 403 y home por rol.
- Las cookies refrescadas se copian también en respuestas de redirección/403.
- Se conserva el bypass de estáticos y `/api`.

### 6.3 Contexto de rol

`apps/web/src/lib/role-context.tsx`

- Eliminados `getCookie`/`setCookie` y toda escritura de `nexo_session`,
  `nexo_role`, `nexo_user_name`.
- `getUser()` + `profiles.role` como única fuente.
- `login(user, redirectTo)` sólo actualiza estado visual y navega con
  `safeRedirectForRole`.
- `logout()` ejecuta `signOut()` y limpia cookies legacy.
- Eliminados `setRole`/`toggleRole` (no se usaban y permitían cambiar el rol
  mostrado).

### 6.4 Login

`apps/web/src/app/(auth)/login/page.tsx`

- Eliminado el fallback de autenticación demo (`isStudentMatch` /
  `isTeacherMatch`): no existe una segunda vía de autenticación.
- Se mantiene el prellenado de credenciales demo como comodidad visual; el
  usuario debe autenticarse realmente contra Supabase.
- El rol se valida con `normalizeRole(profile.role)`; si el perfil no existe o
  no es un rol de portal, se cierra sesión y se deniega.
- Se mantiene la comprobación de portal seleccionado vs. rol verificado.

### 6.5 Clientes API

`apps/web/src/lib/api/client.ts`, `learning.ts`, `content-generation.ts`

- Eliminadas las cabeceras `X-User-Id`, `X-Tenant-Id`, `X-User-Role`,
  `X-Course-Ids`.
- Sólo se envía `Authorization: Bearer <Supabase JWT>`.
- Sin token, la petición se envía sin identidad y el backend responde 401.

### 6.6 SQL (justificado)

`supabase/migrations/20261109000000_profiles_privilege_hardening.sql`

1. `REVOKE UPDATE ON public.profiles FROM authenticated, anon;`
2. `GRANT UPDATE (full_name, avatar_url) ON public.profiles TO authenticated;`
3. Trigger `trg_profiles_prevent_privilege_escalation` que rechaza cambios de
   `id`, `role`, `tenant_id` o `student_code` salvo que el actor sea
   `admin`/`super_admin` o una operación de servidor sin `auth.uid()`
   (`service_role`, migraciones, seeds).

Motivo: FastAPI resuelve permisos desde `profiles.role`. Sin este cambio, la
política RLS de fila permitía a un estudiante modificar su propio rol. No se
debilitó ninguna RLS ni se expuso la service-role key.

## 8. Compatibilidad y límites

- **FastAPI no se modificó.** El contrato de autenticación, validación de
  firma/issuer/audience/expiración, resolución de identidad y permisos sigue
  intacto. El frontend sigue enviando el JWT de Supabase.
- **No se tocaron** modelos predictivos, OpenAPI, arquitectura de despliegue ni
  el diseño de vistas (salvo el comportamiento de login ya descrito).
- **No se agregaron dependencias** ni servicios.
- **No se expuso** `SUPABASE_SERVICE_ROLE_KEY` en el navegador.
- **No se deshabilitó** RLS; se añadieron restricciones de columna y trigger.
- `researcher` y roles admin no tienen portal dedicado; reciben 403 en áreas
  estudiantiles y el shell docente para admin/super_admin. Crear un portal
  admin queda fuera de P0.1.
